# 秒杀链路集成测试

每条测试对应一个「不这么做就会出的事故」，不是为了覆盖率。

| 测试 | 断言什么 | 防的是哪件事 |
|---|---|---|
| `sameRequestIdCreatesExactlyOneOrder` | 同一个 `requestId` 提交两次 → 一张单、库存扣一次、第二次返还**同一个**单号 | 用户重试变重复下单，或者被误导成"没抢到" |
| `concurrentSameRequestIdCreatesExactlyOneOrder` | 50 个线程同时用同一个 `requestId` → 只有 1 个拿到「排队中」，50 个响应里的单号全都一样 | 并发下幂等失效（两个请求同时通过"查"，然后各扣一次） |
| `lostGateRetryHitsUserRequestIndexAndCompensates` | 手工删掉 Redis 幂等门后重试同一请求 → 撞 `uk_user_request` → 消费端撤销扣减，Redis 名额退回 | Redis 丢数据 / 门过期后，那一次扣减永久少卖一件 |
| `noOversellUnderConcurrentLoad` | 库存 100、200 个不同用户同时抢 → 恰好 100 张单、DB 和 Redis 库存都刚好到 0 | 超卖（多卖）和漏卖（少卖） |

## 怎么跑

```bash
# 1. 应用必须先跑起来（黑盒测试，打的是真实端口）
mvn spring-boot:run

# 2. 跑集成测试
mvn -q test -Dtest=SeckillIT
```

一条命令跑完约 30 秒（其中 20 秒是超卖那条要在测试里现场登录 200 个账号、再等消费者建完 100 张单）。

**类名为什么以 `IT` 结尾**：surefire 默认不扫 `*IT.java`。项目里还有一个 `AudiobackendApplicationTests` 是 `@SpringBootTest`，`mvn test` 会连带启动一个完整上下文 —— 包括 RabbitMQ 监听容器。那样就多了一个消费者和正在跑的应用抢消息，测试结果不确定。所以集成测试必须显式指定才跑。

## 几个刻意的选择

**黑盒 HTTP，不启 Spring 上下文。** 除了上面那条理由，还因为黑盒打的是用户真正打的接口：拦截器、令牌桶、Lua、MQ 全在内。白盒直接调 service 会跳过拦截器和 HTTP 层，测出来的东西和线上不是一回事。

**连接信息从 `application.yml` 读**（`TestEnv`），不写在代码里。那个文件里有真实密码，而且已经在 `.gitignore` 里；写死在测试里等于把密码提交进版本库。

**测试隔离**：专用活动 `actId = 900` + 专用用户 `it_seckill_user`，不碰 `actId = 1` 的真实数据。每条测试开始前重置活动（DB 活动行 + Redis 库存 + Redis 元信息 + 已购 + 令牌桶 + 幂等门，少写一处就会测到"看起来对但不是想测的东西"），结束后删掉 `actId = 900` 的订单、明细、支付单和对应的 Redis 键。

**超卖那条要在测试里登录 200 个账号**，而不是在数据库里伪造用户：鉴权要读 Redis 里的 token，伪造用户还得连带伪造 token，那测的就不是真实链路了。登录用 `k6u_*`（`loadtest/seed-tokens.ps1` 批量注册过的压测账号）。并发度用 50 个线程跑 200 个任务，不用 200 个瞬时连接 —— Windows 的 listen backlog 会 RST 掉一部分，那样"少卖"和"超卖"就混在一起分不清了。

## 它抓到的第一个真 bug

第一版跑起来，第一条测试是红的：

```
❌ 第二次应该被判为重复提交，实际是：「已达到限购数量」
```

原因是 `seckill.lua` 的判断顺序：限购（④）在幂等门（⑥）前面。`limitPerUser = 1` 的用户抢到之后 `bought` 已经是 1，第二次请求在 ④ 就被判「超限购」返回了，**永远走不到 ⑥ 去把自己的单号还回来**。

也就是说：用户网络超时重试，看到"你超过限购了"以为没抢到，但他其实有一张订单。幂等门在"一人一单"这个最常见配置下等于不存在。

这也不是新发现 —— `ISSUES.md` 里早就把它记成"已知行为"。测试把它从"记下来"变成了"红的"。

**修法**：把「查门」和「记门」拆开。脚本最前面（令牌桶之前）加一次**只读**的 `GET`，查到就直接返回 `{'7', 原单号}`；「记门」的 `SET NX` 仍在扣减前一行不动。

- 读提前是安全的：`GET` 不产生状态，读不到就什么也没改变。
- 写不能提前：写门是一句"这个 requestId 换到了订单 X"的承诺，提前写就会在售罄、超限购这些分支上留下**不存在的订单号**，用户重试时被告知"你有订单 ORD-x"，去查却查不到，直到 1 天后 TTL 过期。
- 两个分支都必须保留：并发时两个请求可能同时通过开头的 `GET`（都读到 nil），然后在 `SET NX` 那里只有一个成功。

改完那条断言变绿，而且**前三条数据断言（订单数、DB 库存、Redis 库存）在修之前就已经是绿的** —— 说明数据一直是干净的，坏的只是给用户看的那句话。

这也是为什么测试里**把数据断言写在提示语断言前面**：红了能一眼看出是数据错还是话错。
