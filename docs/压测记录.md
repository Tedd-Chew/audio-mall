## 实验 5-4：吞吐与单机上限

同一负载（200 VU、库存 10000、限购 1），分别在「限流开」和「限流近似关闭」下跑：

| 配置 | QPS | P50 | P95 | 说明 |
|---|---|---|---|---|
| 限流开（capacity 500 / 200 每秒） | 604.6 | 325ms | 369ms | 64% 请求是限流快速拒绝 |
| 限流近似关闭（capacity/rate = 100 万） | 615.7 | 317ms | 370ms | **QPS 几乎没变 → 限流不是瓶颈** |

### 并发 → 延迟曲线（限流关闭）

| VU | QPS | P50 | P95 |
|---|---|---|---|
| 10 | 590.9 | **16ms** | 20ms |
| 50 | **769.0** | 62ms | 84ms |
| 100 | 693.1 | 144ms | 166ms |
| 200 | 620.6 | 318ms | 407ms |

**事实**：

1. **单机上限约 700~770 QPS**，在 50 并发时达到峰值；继续加并发，QPS 反而略降
2. 延迟随并发**线性上升**（16 → 62 → 144 → 318ms），符合 Little's Law：`QPS ≈ 并发 / 延迟`
3. 与 Sprint 3 的普通下单（353 QPS）相比翻倍 —— 秒杀把建单搬到了 MQ 消费端，请求路径更短

**按 1 万 QPS 的设计目标推算**：`10000 / 770 ≈ 13 台`。这就是「多实例 + 限流」必须存在的原因。

> 注意这个 13 台是**有前提**的：`QPS_max = 线程数 / 单请求延迟`，770 这个数字建立在「单请求 17ms、200 线程」之上。
> 延迟降一半，单机上限就接近翻倍，需要的机器数就减半。所以「加机器」和「降延迟」是同一件事的两种解法，
> 不该只记着加机器。

## 压测中发现的两个问题

### 问题 1：瞬时 1000 个连接被大量拒绝

1000 个 VU 同时建连时，只有 **207 个请求到达应用层**，其余全是 `connection refused`。

- `accept-count` 从默认 100 调到 1000、再到 4000，**都无效**
- 说明限制不在 Tomcat，在 **Windows 的 listen backlog**

**处理**：改成「200 并发 × 5 轮」，绕开连接层，让业务结论不被环境噪声污染。
代价是并发度从 1000 降到 200 —— 200 抢 100 仍是 2:1 的争抢压力，不影响「不超卖」的验证。

### 问题 2：单请求 17ms，这笔账的拆解

**先纠正一处错话**：之前写"秒杀路径只做 3 次 Redis 操作（token 校验、限流、Lua）"。
数错了 —— `JwtInterceptor` 用 `hasKey` + `get` **两次**查 Redis，实际是：

| 路径 | Redis 往返次数 |
|---|---|
| 拒绝（售罄/限购） | **4**（EXISTS、GET、限流 Lua、秒杀 Lua） |
| 成功（抢到名额） | **5**（上面 4 次 + `HGETALL` 读 meta） |

拆解测量（本机 → Docker，单线程串行 curl，各 60 次）：

| 场景 | 平均 | P50 | P95 |
|---|---|---|---|
| A 不存在的路径（无 handler，不碰 Redis / DB） | 8.15ms | **5.34ms** | 21.03ms |
| B 秒杀拒绝路径（4 次 Redis 往返） | 19.30ms | **16.98ms** | 37.01ms |
| B − A | 11.15ms | **11.64ms** | — |

B − A = 11.64ms，摊到 4 次往返 = **每次 2.9ms**。

同一台机器上用裸 TCP 直连 Redis 测同一件事：

| 方式 | 每次往返 |
|---|---|
| 串行 PING（write→read） | **623µs** |
| 一次写 2000 个 PING（pipeline） | **1.65µs/条** |

**两个事实**：
1. Redis 服务端处理一条命令只要 1.65µs —— 瓶颈不在 Redis 的 CPU
2. 应用里一次往返 2.9ms，是裸 TCP 623µs 的 **4.7 倍**，多出来的 ~2.3ms 在应用侧链路里（Lettuce 线程交接、Docker 端口转发）

**顺带发现一个死配置**：`application.yml` 里 `lettuce.pool.max-active: 8` 对这条链路**完全不生效**。
Lettuce 默认 `shareNativeConnection=true`，普通命令全部走一个共享连接，pool 只在关闭共享后才真正借连接。
这行配置让人以为"配了连接池"，实际没配。要么删掉，要么显式设 `share-native-connection: false` 才生效。

**仍未定位**：为什么并发从 10 涨到 200，QPS 只从 590 到 620（几乎平），而延迟从 17ms 涨到 318ms（18 倍）。
如果 200 个请求真能各自独立跑完 17ms，200 线程应该能到 `200 / 0.017 ≈ 11700 QPS`，实测只有 629。
说明存在一个 **~700 请求/秒的串行化资源**，位置未知。下一个实验见「待做实验」。

## 实验 5-6：把每请求 Redis 往返从 5 压到 2

> 这一轮跳过了 E1，直接做 E3 的改法。原因：改法本身没有语义风险，先做能把"往返数"这个变量直接钉死在压测上。

### 改了什么

| 项 | v1 | v2 |
|---|---|---|
| 鉴权 | `EXISTS` + `GET` 两次 | 只 `GET` |
| 限流 | 独立 Lua，Java 里 catch 后**放行** | 并进秒杀 Lua，出错即拒绝 |
| 活动信息 | 成功后 `HGETALL` 一次 | 由秒杀 Lua 一起返回 |
| 脚本命令数（成功路径） | 3 + 7 + 1 = 11 条，3 次往返 | 9 条，1 次往返 |

### 变量与常量

- **变量**：每请求 Redis 往返次数
- **常量**：同一 k6 脚本（`MODE=throughput`, 200 VU, 30s）、库存 10000、限购 1、令牌桶 500 / 200 每秒、先跑 `reset.ps1`、同一台机器

### 按 v1 的拒绝分布推算平均往返数

v1 在 200 VU / 库存 10000 / 桶 500 的条件下，约 64% 被限流、33% 成功、3% 售罄限购：

| 请求类型 | 占比 | v1 往返 | v2 往返 |
|---|---|---|---|
| 被限流 | 64% | JWT 2 + 限流 1 = **3** | **2** |
| 售罄 / 限购 | 3% | 2 + 1 + 1 = **4** | **2** |
| 成功 | 33% | 2 + 1 + 1 + HGETALL 1 = **5** | **2** |
| **加权平均** | | **3.69** | **2.00** |

### 跑之前写下的预期

单次往返实测 2.9ms，则 Redis 部分从 `3.69 × 2.9 = 10.7ms` 降到 `2 × 2.9 = 5.8ms`，每请求少 **4.9ms**。

| 假设 | 单请求延迟 | 预测 QPS（200 VU，`QPS = 200 / 延迟`） |
|---|---|---|
| 成本确实按往返次数计费 | 17ms → 12.1ms | 620 → **约 870（+40%）** |
| 另有不按往返计费的串行资源 | 基本不变 | 620 → **620±5%** |
| 部分按往返计费 | — | 700~800 |

**判据**：QPS 涨到 800 以上 → 往返次数是真变量，继续压；纹丝不动（<5%）→ 那 2.9ms 不是往返数的线性成本，得回去做 E1 找串行资源。

### 结果

先跑了 5-1 / 5-2 / 5-3 确认原子性没被合并破坏：

| 实验 | 结果 |
|---|---|
| 5-1 不超卖（1000 用户抢 100 件） | 成功 **100**、售罄 664、限流 236；库存 0、订单 100、已购用户 100 → 四数一致 ✅ |
| 5-2 一人一单（1 用户 × 200 并发） | 成功 **1**、限购 199、库存 100→99 ✅ |
| 5-3 限流（1000 突发） | 限流拒绝 **263**，其余进入库存判断 ✅ |

吞吐（每轮都先 `reset.ps1`，库存 10000、限购 1、桶 500/200）：

| 配置 | v1 基线 | v2 第 1 次 | v2 第 2 次 | 变化 |
|---|---|---|---|---|
| 50 VU / 20s | **769.0 QPS** | 843.1 | 895.8 | **+13%** |
| 200 VU / 20s | **620.6 QPS**，平均延迟 320.6ms | 727.1（274ms） | 744.6（267ms） | **+19%**，延迟 −15% |

### 结论

**1. 改动本身是对的**：三个正确性实验全过，往返数从 3.69 降到 2.00，吞吐确实涨了 13~19%。

**2. 但远低于预测的 +40%。** 按 `S = F + N·r` 反推固定成本 F：

- 50 VU：`1.13 = (F + 3.31r) / (F + 2r)` → `F ≈ 8.1r ≈ 23ms`
- 200 VU：`1.19 = (F + 3.31r) / (F + 2r)` → `F ≈ 5.0r ≈ 15ms`

两个估算不一致（模型太粗），但都指向同一件事：**单请求成本里固定部分（框架、线程、序列化、日志、MQ、Docker 转发）是每次往返成本的 5~8 倍**。省往返能扭动的只是那小半。

**3. 「单机上限 770 QPS」这个说法要改。** 50 VU 现在能跑到 896 QPS，说明它不是一堵固定的墙，而是 `QPS ≈ 并发 / 延迟`，延迟降了上限就跟着抬。之前把 770 当成硬上限去推「需要 13 台」，估偏了。

**4. 下一步该做的是 E1，不是继续压往返。** 固定成本 15~23ms 是大头，而我们至今没定过它的位置。继续合并往返（比如把 JWT 也搬进 Lua）最多再省 2.9ms，收益递减。

## 实验 5-7（E1）：三级阶梯 —— 上限到底在哪一层

### 目的

秒杀链路现在是 747 QPS（200 VU）。这个上限属于**应用框架**、**MySQL**、还是**Redis / MQ**？

### 设计

同一个 k6 进程、同一台机器、同样的并发，**只换被请求的路径**，一层层往上加组件：

| 阶梯 | 路径 | 会经过什么 | 会不会碰 Redis |
|---|---|---|---|
| L1 | `/api/nope` | Tomcat → DispatcherServlet → 404。<br>没有 handler，**Spring 根本不会建立拦截器链** | 不碰 |
| L2 | `/api/seckill/1` | 加上 Controller + Service + **一次 MySQL select**（读活动详情）。<br>在 `excludePathPatterns` 里，不鉴权 | 不碰 |
| L3 | `/api/order/seckill/1` | 全链路：鉴权查 Redis 1 次 + Lua 1 次 + 命中则投 MQ | 2 次往返 |

- **变量**：被请求的路径（即“这条链路上有哪些组件”）
- **常量**：k6 进程、机器、VU 数（200）、时长（20s）
- **指标**：QPS、平均延迟、P95

### 跑之前写下的预期

| 阶梯 | 预期 QPS | 依据 |
|---|---|---|
| L1 `/api/nope` | **2000 ~ 4000** | 纯框架，无 IO。参考：单线程 curl 测这个路径 P50 是 5.3ms |
| L2 `/api/seckill/1` | **500 ~ 1500** | 一次 MySQL select。Sprint 3 的普通下单（含写库）是 353 QPS |
| L3 `/api/order/seckill/1` | **747**（已知，v2 实测） | — |

### 判据

| 看到什么 | 结论 |
|---|---|
| L1 ≥ 2000 | 框架能扛几千 QPS，秒杀卡在 IO 层 |
| L1 < 1000 | **上限在 Tomcat / k6 / 这台机器本身**，前面所有“Redis 是瓶颈”的推论都要重写 |
| L2 明显低于 L1 | MySQL 是主要成本之一 |
| L2 与 L3 接近 | MySQL 占比小，问题集中在 Redis / MQ |

### 结果（200 VU / 20s，三次都是同一台机器、同一个应用实例）

| 阶梯 | QPS | 请求数 | 平均 | 中位 | P95 |
|---|---|---|---|---|---|
| L1 `/api/nope` | **15,545.7** | 311,143 | 12.2ms | 10.6ms | 29.9ms |
| L2 `/api/seckill/1` | **4,482.4** | 89,769 | 44.3ms | 33.8ms | 119.4ms |
| L3 `/api/order/seckill/1` | **757.0** | 15,219 | 263.1ms | 227.4ms | 385.6ms |

### 结论

**1. 上限不在 Tomcat / k6 / 操作系统。** L1 跑到 15,545 QPS，是 L3 的 **20 倍**。之前“这台机器只能跑 700~900”的怀疑被推翻 —— 机器和压测工具都有余量。

**2. MySQL 也不是上限。** L2 一次查询仍有 4,482 QPS，是 L3 的 5.9 倍。

**3. 那么瓶颈在 Redis 的取数路径上。** 而且这次算出了一个很稳的数：

V2 拒绝路径（占 L3 流量的 70%）里，每条请求打给 Redis 的命令是：

| 来源 | 命令 |
|---|---|
| `JwtInterceptor` 的 GET | 1 |
| `seckill.lua` 走到 `return {'6'}` 之前（HMGET + HSET + PEXPIRE） | 3 |
| **合计** | **4 条** |

`757 QPS × 4 = 3,028 条命令/秒`。

再拿 v1 的基线核对。v1 拒绝路径是 5 条命令（EXISTS + GET + 限流 Lua 的 3 条），当时测到 620 QPS：

`620 QPS × 5 = 3,100 条命令/秒`。

**两次改动、两套代码、两个不同的 QPS，算出来的命令吞吐是 3,028 和 3,100 —— 差 2%。**

这解释了为什么“往返从 3.69 降到 2.00、QPS 只涨 22%”：**真正守恒的是每秒经过这条 Redis 连接的「命令条数」，约 3,050 条/秒**，不是请求数，也不是往返数。合并 Lua 只减少了 1 条命令（5→4），所以 QPS 只涨了 22%。

那个数怎么来的：`1 秒 ÷ 3,050 = 328µs` 每条命令。而裸 TCP 实测一次往返是 623µs —— 说明命令确实在做**少量合并**（约 2 条/往返），但远没有把连接用满（pipeline 测试里这条通道能跑 60 万条/秒）。

**4. 按这个模型反推要多少实例**：目标 1 万 QPS、每请求 4 条命令 → 需要 40,000 命令/秒，是当前的 13 倍。所以“13 台”这个量级其实没错（`40000/3050 ≈ 13`），只是它的依据不是“770 QPS 上限”，而是“每条连接每秒只能过 3,050 条命令”。

**5. 下一个实验（E2）的判据已经很清楚了**：把 `share-native-connection` 关掉、`max-active` 开到 32，连接数从 1 条变成最多 32 条。如果“3,050 条/秒是每条连接的上限”，那么命令吞吐应该按连接数增加；如果它纹丝不动，说明限制在更下面（Docker 转发 / Redis 服务端）。

> 注意这里的因果链仍然是**假设**：它由两个数据点吻合推出来（3,028 / 3,100），还没有独立验证。E2 就是为它设计的。
