### 实验 B-2：调整 fsync 配置后重测

2026-10-21

**改动**（只为模拟生产 SSD 的开销，生产必须保持 1 / 1）：

```sql
SET GLOBAL innodb_flush_log_at_trx_commit = 2;   -- 原 1
SET GLOBAL sync_binlog = 0;                      -- 原 1
```

应用重启后重测，参数同上（200×10，分散）。

| 项 | 改前（B） | 改后（B-2） | 变化 |
|---|---|---|---|
| 总耗时 | 11,590 ms | **5,657 ms** | -51% |
| QPS | 172.56 | **353.54** | **+105%** |
| P50 | 661 ms | **396 ms** | -40% |
| P95 | 2,624 ms | **1,787 ms** | -32% |
| P99 | 3,583 ms | **2,268 ms** | -37% |
| 成功 | 2000 | 2000 | — |

**事实**：仅改两个持久化参数，QPS 翻倍。说明 WSL2 虚拟磁盘的 fsync 开销至少贡献了一半的耗时。

**仍有疑问**：改后单请求平均 56ms（20 连接 ÷ 353 QPS），本地环回 + 无磁盘等待，还是偏慢，可能还有别的因素（客户端与应用同机争 CPU）。

## 实验 C：库存有限并发抢购

2026-10-20　`SAME_PRODUCT=true`，`500` 并发，库存 100

| 项 | 值 |
|---|---|
| 并发 | 500 线程 × 10 次 = 5000 请求 |
| 商品 | `productId = 4`，初始库存 100 |
| 总耗时 | 15,589 ms |
| QPS | 320.74 |
| 成功 / 库存不足 / 失败 | **100 / 4900 / 0** |
| P50 / P95 / P99 | 997 / 6068 / 6567 ms |
| Max | 6948 ms |

**数据库验证**：

| 项 | 值 |
|---|---|
| `product.stock` | **0** |
| `orders` | **100** |
| `order_item` | **100** |
| `payment` | **100** |
| 订单金额 | 全部 999.00 |

**事实**：5000 个请求抢 100 件，成功正好 100，库存归零，三张表数量一致。**没有超卖，也没有少卖。**

## 待查

- 每个请求平均耗时约 116ms（B 实验），本地 MySQL 单条 SQL 应该 1ms 以内，差了两个数量级
- 嫌疑：`innodb_flush_log_at_trx_commit=1` 每次事务 fsync，而 Docker on WSL2 的磁盘 IO 较慢
