# 一、三句话版本

被要求"介绍一下这个项目"时：

1. 秒杀的正确性我做了两道闸：Redis 的幂等键挡重复提交，数据库的唯一索引兜住漏网的。
2. 压测时我先以为瓶颈是 Redis，后来发现是日志级别开成 DEBUG、同步写盘——改回 INFO 吞吐翻了 2.7 倍。所以我不看 CPU 高低判断瓶颈，我改一个变量看差值。
3. 部署到 4 核服务器之后瓶颈变成带宽了：3 Mbps 只够 900 次/秒，这时候谈 CPU 和架构都没意义。

# 二、幂等

## 幂等键会过期吗？跟活动一起过期吗？

**不跟活动。幂等键固定 24 小时；跟活动走的是"已购标记"，过期时间 = 活动结束 + 1 天。**

为什么这么分：看这个 key 过期之后是"错误"还是只是"变慢"。

- 已购标记过期 → 限购失效，同一个人能再抢一单 → **真错误**，必须覆盖活动全程
- 幂等键过期 → 退回慢路径，数据库唯一索引还在 → 只是变慢，可以短

一句话：**快路径可以短命，正确性必须永久。**

→ 追问：那 24 小时后重发会怎样？

## 24 小时后同一个 requestId 再来，会出第二张单吗？

**不会。** 走一遍：

1. Lua 开头的只读 GET 未命中（key 过期了）
2. 限流、时间窗、库存都过
3. **限购先挡住**：已购记录里有这个人，`limit_per_user=1` 直接拒绝
4. 就算限购是 5 件、还没买满：`SET NX` 成功 → 扣库存 → 入队
5. 消费端 INSERT 撞 `uk_user_request`，按**新单号**查不到订单 → 判定真实冲突 → **回滚名额** → ack

结果：不出第二单，名额扣了又还回去，账是对的，只是白跑一趟。

原因就一个：`uk_user_request` 这个唯一索引是永久的，跟着订单表走，不受 Redis TTL 影响。

## requestId 不传会怎样？

**等于完全没有幂等，而且两处同时失效。**

- Lua 里 `ARGV[7]='0'`，压根不写幂等键
- MySQL 的唯一索引**允许多个 NULL**，`(user_id, NULL)` 可以插无数次

这是真隐患：Nginx 配了 `proxy_next_upstream`，超时会重试，同一个 POST 可能被处理两次。所以生产必须把 requestId 改成必填。

## 幂等键写成功了，但消息没发出去怎么办？

**catch 住发送异常，把名额和幂等键一起还回去。**

必须连幂等键一起删，否则用户重试会命中幂等门、拿到一个**根本不存在的订单号**。代码注释里写的就是这句。

## 回滚名额会不会被执行两次？

**不会。** 回滚本身是个 Lua 脚本，守卫条件是"幂等门里存的单号，是不是这一条消息的单号"。撤销成功会删门，第二次调用什么也做不了。

失败时只记日志、不抛异常。注释里的取舍是原话：**"宁可少卖一件（名额没还回去），不可超卖（名额还两次）"**——抛出去只会让消息重投，把问题放大。

## 两个实例同时收到同一个 requestId？

**只有一个成功。**

`SET NX` 是原子的。两个请求即使落在不同 JVM，到 Redis 上也是串行的。写失败的那个 GET 出 orderNo 原样返回。

这点值得强调：**这里不需要分布式锁**。很多人第一反应是"加个 Redis 锁"，其实 `SET NX` 本身就是那把锁，而且不用解锁。

# 三、库存与一致性

## Redis 库存和 MySQL 库存，哪个是真的？

**Redis 是"名额"的权威，MySQL 是"账本"。**

抢购瞬间只有 Redis 算数，所有扣减在 Lua 里原子完成，所以不超卖。MySQL 那边由消费端用条件 UPDATE（`WHERE stock >= n`）维护，最终和 Redis 对上。

一旦 DB 判"真实冲突"，必须把 Redis 名额加回去，否则名额凭空消失，表现是"明明没卖完却抢不到"。

## 服务重启，Redis 里的库存没了怎么办？

**启动时从 `seckill_activity` 表把未结束活动的库存预热回 Redis。**

关键是**不能覆盖已存在的 key**：两个实例同时启动会各写一次，后起的会覆盖先起的，把已经扣掉的库存"复活"。所以用 `SET NX` 语义，已存在就不动。

再往下问"Redis 在活动进行中挂掉并丢了数据"——只能按 DB 重新预热，会多卖一点。这也是 Redis 开了 `appendonly yes` 的原因。

## 活动结束，秒杀剩下的库存去哪了？

**回补到商品库存（`product.stock`）。**

创建活动时是"从商品库存里划出 100 件"，结束不回补，商品库存就永久少一块。这个任务用条件 UPDATE 保证多实例下也只执行一次。

## 怎么证明真的不超卖？

两条独立证据：

1. **集成测试**：100 件库存、200 并发，最后核对成功单数 = 100、没有重复用户、Redis 库存 = 0 且不为负
2. **压测核对脚本**：压完比对 DB 订单数、Redis 库存、已购人数三者一致

为什么两个都要：测试证明逻辑对，压测证明并发下行为对（连接复用、超时、重试都掺在里面）。

## 超卖的两条路径，分别被谁挡住？

| 路径 | 挡住它的东西 |
|---|---|
| 并发扣减时"读-改-写"交错 | Lua 在 Redis 内部单线程执行，中间插不进别的命令 |
| 扣了 Redis 但 DB 写失败 | DB 的 `WHERE stock >= n` + 事务回滚，然后回滚 Redis 名额 |

这两条要**分别**防。Redis 挡的是并发，DB 挡的是最终一致。

# 四、消息队列

## 为什么手动 ack，不用自动 ack？

自动 ack 是"消息一到就确认"，这时进程崩了或写库失败，消息已经没了——订单就丢了。

手动 ack 是"处理成功才确认"，做不到就不确认，消息回队列重投。**代价是可能重复消费**，所以幂等兜底和手动 ack 是配套的：用"可能重复"换"不会丢"，这个交换没法两全。

## 消息重复投递了怎么处理？

**按订单号能不能查到来区分两种情况。**

| 撞的索引 | 含义 | 处理 |
|---|---|---|
| `uk_order_no` | 同一条消息重投，订单早建好了 | ack，什么都不做 |
| `uk_user_request` | 同一用户另一张单真抢到了，本次多余 | 回滚名额 + ack |

不能一律当重复：真实冲突被当成功的话，名额就永久少一个。

## 消息发出去了但 broker 没收到？

**这条现在是敞开的，得主动承认。**

配了 `publisher-confirm-type: correlated`，但代码里没有实现 `ConfirmCallback`。所以：

- 连接异常、broker 不可用 → `convertAndSend` 抛异常 → 被 catch → 回滚名额 ✅
- 交换机不存在、路由不到、broker 收了但落盘前崩 → **消息静默丢失，代码感知不到** ❌

面试时主动说："我知道这里该配 confirm 回调，当前没做。队列和交换机是代码声明的，路由错误概率低，但 broker 宕机窗口确实会丢。"

## 死信队列里的消息怎么办？

**目前只进不出。** 声明了 DLX 和 DLQ，重试耗尽会进去，但没有监控、没有重放工具。

网上常说"进死信就安全了"，其实不对。没有处置的死信队列就是"消息坟墓"，问题被静默吞掉。

## 消费端的并发和 prefetch 怎么定的？

`concurrency: 2, max-concurrency: 4, prefetch: 10`。

prefetch 是"每个消费者最多预取多少条未确认的消息"。太大 → 一条卡住会拖住一堆；太小 → 吞吐上不去。10 是折中。

实测把并发从 1 调到 4，吞吐没提升（25.4 / 29.0 / 26.6 单/秒），说明瓶颈不在并发数——见下面那条。

# 五、性能与瓶颈

## 怎么判断瓶颈在哪？

**改一个变量，看吞吐差多少。不看 CPU 占用。**

反例是我自己踩的：Redis CPU 最高（0.66 核），我判"瓶颈是 Redis"。后来把日志从 DEBUG 改回 INFO，吞吐 3,883 → 10,900。真凶是**日志同步写盘压在请求线程上**。

为什么误判：CPU 高只说明"它干活多"，不说明"别人在等它"。判断瓶颈要看**谁在排队**。

## 消费端为什么只有 29 单/秒？

一条消息的事务里有 4 条 SQL + commit，其中 `UPDATE seckill_activity WHERE id=1` **持行锁到事务提交**。所有消费者抢同一行，等于被串行化。

证据：并发 1/2/4 → 25.4 / 29.0 / 26.6 单/秒，单条耗时 39.4 / 68.9 / 150.6 ms。并发越高单条越慢，这是排队的特征，不是 CPU 不够。

## 双实例为什么吞吐不涨？

**瓶颈在共享资源上，不在应用进程里。**

实测 200 并发：单实例 10,575 QPS，双实例 10,452 QPS。两个 JVM 抢同一个 Redis、同一份连接。

所以双实例的意义是**可用性**：杀一个实例，30 次请求全部成功，切换约 2 ms。

## 1000 并发时为什么大量连接被拒？

Tomcat 的 `accept-count` 默认 100。工作线程全忙时新连接最多再排 100 个，超出的直接 RST，实测约 46% 被拒。

改成 1000 能让瞬时建连排上队，但**治不了根**——后端处理不过来，排队的最终也会超时。真正的解法是限制入口流量。

## k6 怎么用？

**开源的负载测试工具，用 JavaScript 写脚本，命令行跑。**

```js
export const options = {
  scenarios: { main: { executor: 'constant-vus', vus: 200, duration: '30s' } },
  thresholds: { http_req_failed: ['rate<0.01'] },
};
export default function () {
  http.get(`${__ENV.BASE_URL}/api/product/1`);
}
```

- 跑：`k6 run -e VUS=200 -e DURATION=30s script.js`
- 看：`http_reqs.rate` 是 QPS，`http_req_duration` 的 `p(95)` 是长尾，`http_req_failed` 是错误率
- 场景两种：`constant-vus` 固定并发测稳态，`ramping-vus` 爬坡找拐点
- 我们用它压秒杀和商品详情，10,900 QPS 那组就是它跑的

注意 `thresholds` 没达标时 k6 会以非零码退出，这是特性不是 bug。

# 六、可靠性（都有实测）

## Redis 挂了会怎样？

**改之前假死，改之后 1 秒内返回 503。**

| | 改前 | 改后 |
|---|---|---|
| 单请求耗时 | 60,087 ms | 1,043 ms |
| 响应 | HTTP 200 + `code:401 "Token解析失败"` | `code:503 "系统繁忙"` |
| 恢复后首个请求 | 24,318 ms | 74 ms |

为什么是 60 秒：`spring.data.redis.timeout` 不配就默认 60 秒，200 个工作线程全被占住。

为什么 503 也重要：401 是"你没登录"，503 是"服务暂不可用"。**错误码给错，调用方会做错决定**——重新登录 vs 重试。

## MySQL 挂了会怎样？

**一条消息占住消费线程很久。改前 115 秒，改后 41 秒。**

账是这么算的：`hikari.connection-timeout` 20 秒 × 重试 5 次 + 退避 1+2+4+8 = 115 秒。改成 5 秒 → 5×5+15 = 40 秒。

这两个数是同一个数：超时越长，能自动扛住的停机越久，但每条消息占线程也越久。选 5 秒的依据是 MySQL 容器重启实测 6.2 秒，40 秒有 6 倍余量；再长的停机是故障不是重启，应该告警加重放。

# 七、部署与安全

## 生产为什么关 Swagger？

SpringDoc 默认开着，`/v3/api-docs` 返回完整接口清单，`/swagger-ui` 是可交互调用页面。部署到公网 IP 后实测两个都是 200，等于把攻击面清单送给外面。

有个坑：本项目所有响应都是 HTTP 200 + 业务 code，**看状态码判断"关没关"是无效的，必须看响应体**。

## 为什么数据库和应用端口只绑 127.0.0.1？

公网只应该看到 80。Docker 的 `-p 3306:3306` 默认绑 `0.0.0.0`，必须显式写 `127.0.0.1:3306:3306`；应用配 `server.address: 127.0.0.1`，只让 Nginx 访问它。

## 密码和密钥放哪？

全部走环境变量，`application-prod.yml` 只写 `${ENV}` 占位，**而且故意不给默认值**。

给了默认值，漏配的时候应用会带着开发密码静默启动——你看到"启动成功"，实际连的错库、用的弱密钥。宁可起不来。

# 八、数字口径

| 数字 | 口径 | 能不能说 |
|---|---|---|
| 10,900 QPS | 本机 8C16T、200 并发、纯读 | 加限定可以说 |
| 2.7 倍 | DEBUG → INFO 的吞吐差 | 可以说，有对照 |
| 30 次全成功、约 2 ms | 双实例故障切换 | 可以说 |
| 419 / 7,214 / 5,159 | 4 核服务器：公网 / 回环 / 经 Nginx | 口头说，简历不写死 |
| 29 单/秒 | 消费端，行锁导致 | 可以说，是"发现瓶颈"的素材 |
| 100 库存 200 并发零超卖 | 集成测试 | 可以说 |

简历上出现"1.1 万 QPS"时必须带"本机"，否则一问配置就露馅。
