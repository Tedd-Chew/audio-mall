# 面试问答

> 这份文档只收**能暴露设计深度**的问题：那种"答得出来说明真做过、答不出来说明只是照着教程抄"的。
> 每条给三部分：结论 / 为什么 / 追问会到哪。数字和结论都能在 `docs/` 里找到实验记录。

## 怎么用

1. 先自己答一遍，卡住的地方做记号
2. 只看"结论"，看能不能自己补出"为什么"
3. 最后一节「我现在答不上的」是故意留的——**知道自己哪里会崩，比背熟 20 条更有用**

# 一、幂等

## Q1：幂等键会过期吗？跟活动一起过期吗？

**结论**：不跟活动。幂等键固定 **24 小时**（`seckill.lua:165` 的 `SET NX EX 86400`）；
真正跟活动走的是**已购标记** `audio:seckill:bought:{actId}`，过期时间是 `活动结束时间 + 1 天`（`seckill.lua:181`）。

**为什么不对称**：看这个 key 过期之后会变成"错误"还是只是"退化"。

| key | 过期后的后果 | 判定 |
|---|---|---|
| 已购标记 | 限购失效，同一个人能再抢一单 | **真错误** → 必须覆盖活动全程 |
| 幂等键 | 退回慢路径，数据库唯一索引还在 | 只是退化 → 可以短 |

一句话：**快路径可以短命，正确性必须永久。**

**追问会到哪**：→ Q2（24 小时后真重发会怎样）、Q3（DB 那道闸为什么能兜住）。

---

## Q2：24 小时后同一个 requestId 再来，会不会出第二张单？

**结论**：不会。走一遍就知道：

1. Lua 开头的只读 `GET` 未命中（key 过期了）
2. 令牌桶、时间窗、库存这几关都过
3. **限购这层先挡住**：`HGET bought userId` 发现已买过，`limit_per_user=1` 的话直接返回「已达限购」
4. 就算限购是 5 件、用户只买了 1 件，这层放行 → `SET NX` 成功 → 扣库存 → 入队
5. 消费端 `INSERT` 撞 `uk_user_request` → 按**新 orderNo** 查不到订单 → 判定「真实冲突」→ **回滚名额** → ACK

净效果：不出第二单，名额扣了又还回去，账是对的。代价只是白跑一趟。

**为什么**：`uk_user_request (user_id, request_id)` 这个唯一索引是**永久**的，跟着订单表走，不受 Redis TTL 影响。

**追问会到哪**：→ Q4（`requestId` 不传时这道闸就没了）。

---

## Q3：`requestId` 不传会发生什么？

**结论**：**完全没有幂等保护**，而且是两处同时失效：

```sql
`request_id` VARCHAR(64) DEFAULT NULL
UNIQUE KEY uk_user_request (`user_id`, `request_id`)
```

1. Lua 侧：`ARGV[7]='0'` 时不写幂等键（`seckill.lua:164` 的判断）
2. DB 侧：**MySQL 唯一索引允许多个 NULL**，`(user_id, NULL)` 可以重复插无数次

**为什么这是隐患**：Nginx 配了 `proxy_next_upstream`，超时会重试一次——同一个 POST 可能被处理两次。所以生产必须把 `requestId` 改成必填。这是已知限制第一条。

**追问会到哪**：→ Q15（Nginx 为什么会重试）。

---

## Q4：幂等键写成功了，但消息没发出去，怎么办？

**结论**：`enqueue()` 里 catch 住发送异常，调 `compensate()`——**把名额和幂等键一起还回去**（`SeckillOrderServiceImpl:123-131`）。

**为什么必须连幂等键一起删**：只还库存不删门的话，用户重试会命中幂等门、拿到一个**根本不存在的订单号**。代码注释里写了这句原话。

**追问会到哪**：→ Q5（回滚本身会不会重复执行）。

---

## Q5：回滚名额会不会被执行两次？消息重投呢？

**结论**：不会。`compensate` 是一个 Lua 脚本，守卫条件是「**幂等门里存的单号，是不是这一条消息的单号**」。撤销成功会删门，第二次调用什么都做不了，返回 0。

**为什么这么设计**：消费者重试会让它被调用多次，所以它自己必须幂等。

**失败时怎么办**：只记日志、不抛异常。注释里的取舍写得很直白——**"宁可少卖一件（名额没还回去），不可超卖（名额还两次）"**。抛出去只会让消息再次重投，把问题放大。

**追问会到哪**：→ Q10（少卖一件怎么办）、Q12（MQ 重试）。

---

## Q6：两个实例同时收到同一个 requestId，会怎样？

**结论**：只有一个成功，另一个拿到「重复提交」。

**为什么**：`SET ... NX` 是原子的。两个请求即使同时到达两个 JVM，落到 Redis 上是串行的，只有一个能把键写进去。写失败的那个 `GET` 出 orderNo 原样返回。

**关键点**：这件事**不需要分布式锁**。很多人第一反应是"加个 Redis 分布式锁"，其实 `SET NX` 本身就是那个锁，而且是原子的、不用解锁。

---

# 二、库存与一致性

## Q7：Redis 里的库存和 MySQL 里的库存，哪个是真的？

**结论**：**Redis 是"名额"的权威，MySQL 是"账本"**。两者职责不同。

- 抢购瞬间，唯一权威是 Redis：所有扣减都在 Lua 里原子完成，所以不会超卖。
- MySQL 的 `stock` 由消费端用条件 UPDATE（`WHERE stock >= n`）维护，最终要和 Redis 对上。
- 一旦 DB 判定「真实冲突」，必须把 Redis 名额加回去——否则名额凭空消失，表现是"明明没卖完却抢不到"。

**追问会到哪**：→ Q8（Redis 全丢了怎么办）。

---

## Q8：服务重启，Redis 里的库存没了怎么办？

**结论**：`SeckillWarmUpRunner` 在启动时从 `seckill_activity` 表把未结束活动的库存预热回 Redis。

**关键细节**：预热**不能覆盖已存在的 key**——两个实例同时启动会各写一次，如果后起的覆盖先起的，就会把已经扣掉的库存"复活"。所以用 `SET NX` 语义：已存在就不动。

**追问会到哪**：→ 如果 Redis 在活动**进行中**挂掉并丢了数据（没开持久化），Redis 里已经扣掉的量就找不回来了，只能按 DB 的 `seckill_activity.stock` 重新预热，会多卖出一些。这是 Redis 有持久化（`appendonly yes`）的原因。

---

## Q9：活动结束，秒杀剩下的库存去哪了？

**结论**：`SeckillActivityCloseTask` 在活动结束后把 `seckill_activity.stock` 里剩下的量**回补到 `product.stock`**。

**不做会怎样**：创建活动时是"从商品库存里划出 100 件"，活动结束剩下的不回补，商品库存就**永久少了一部分**。代码注释里写的就是这句。

**追问会到哪**：这个任务用条件 UPDATE 保证多实例下也只执行一次（`WHERE status=1 AND end_time < NOW()`）。

---

## Q10：怎么证明它真的不超卖？

**结论**：两条独立证据。

1. **集成测试**：`SeckillIT` 里 100 库存、200 并发，最后核对：
   - 成功订单数 = 100
   - `orders` 里没有重复的 user
   - Redis 库存 = 0，且不为负
2. **压测核对脚本**：`loadtest/verify.ps1` 压完之后比对 DB 订单数、Redis 库存、已购人数三者是否一致。

**为什么要两个**：测试覆盖的是逻辑正确，压测覆盖的是并发条件下的真实行为（包括连接复用、重试、超时）。

---

## Q11：超卖的两条可能路径，分别被谁挡住？

| 路径 | 挡住它的东西 |
|---|---|
| 并发扣减时"读-改-写"交错 | Lua 在 Redis 内部单线程原子执行，检查与扣减之间插不进别的命令 |
| 扣了 Redis 但 DB 写失败 | DB 的 `WHERE stock >= n` 条件 UPDATE + 事务回滚，然后回滚 Redis 名额 |

**关键认知**：这两条路径要**分别**防，不是靠一个机制。Redis 挡住的是并发，DB 挡住的是最终一致。

---

# 三、消息队列

## Q12：为什么用**手动 ack**，不用自动 ack？

**结论**：自动 ack 是"消息一到就确认"，这时进程崩了或者写库失败，消息已经没了——**订单丢了**。手动 ack 是"处理成功之后才确认"，做不到就不确认，消息回队列重投。

**代价**：可能重复消费。所以幂等兜底和手动 ack 是**配套的**——用"可能重复"换"不会丢"。这个交换必须有，没法两全。

**追问会到哪**：→ Q13（重复了怎么办）。

---

## Q13：消息重复投递了怎么办？

**结论**：`SeckillOrderListener` 捕获 `DuplicateKeyException`，然后**按订单号能不能查到**来区分两种情况：

| 撞的索引 | 含义 | 处理 |
|---|---|---|
| `uk_order_no` | 同一条消息重复投递，订单早建好了 | ACK，什么都不做 |
| `uk_user_request` | 同一用户另一张单真抢到了，本次多余 | 回滚名额 + ACK |

**为什么不能一律当重复**：注释里的原话是"判据是「按 order_no 能不能查到」"。一律当重复的话，真实冲突会被当成成功，**名额永久少一个**。

**追问会到哪**：→ Q5（回滚的幂等守卫）。

---

## Q14：消息发出去了，但 broker 没收到，怎么办？

**结论（诚实版）**：**这条现在是敞开的。**

`application.yml` 里配了 `publisher-confirm-type: correlated`，但代码里**没有实现 `ConfirmCallback`**（全仓库搜不到）。也就是说：

- 连接异常 / broker 不可用 → `convertAndSend` 抛异常 → 被 catch → 回滚名额 ✅ 已覆盖
- 交换机不存在、路由不到、broker 收了但落盘前崩 → **消息静默丢失，代码感知不到** ❌ 未覆盖

**为什么没做**：队列和交换机都由 `RabbitConfig` 声明，路由不到的概率很低；但这是个真实的缺口，正规做法是 `setConfirmCallback` + 失败重投或落"本地消息表"。

**面试时怎么讲**：主动说出来，比被问出来强。可以说"我知道这里应该配 confirm 回调，当前版本没做，队列是代码声明的所以路由错误概率低，但 broker 宕机窗口确实会丢。"

---

## Q15：死信队列里的消息怎么办？

**结论（诚实版）**：目前只进不出——`RabbitConfig` 声明了 DLX 和 DLQ，消息重试耗尽会进去，但**没有监控、没有重放工具**。

**这意味着什么**：网上常说"进死信就安全了"，其实不对。没有人工/自动处置的死信队列只是个"消息坟墓"——问题被静默吞掉了。

**正规做法**：DLQ 深度告警 + 一个后台页面能查看并重放。

---

## Q16：消费端的并发和 prefetch 怎么定的？

**结论**：`concurrency: 2, max-concurrency: 4, prefetch: 10`。

**为什么**：prefetch 是"每个消费者最多预取多少条未确认的消息"。太大 → 一条卡住的消费会拖住一堆消息；太小 → 吞吐上不去。10 是在"吞吐"和"故障影响面"之间的折中。

**关键实测**：消费并发从 1 调到 4，**吞吐没有提升**（25.4 → 29.0 → 26.6 单/秒），说明瓶颈不在并发数上，而在一个串行化的资源——参见 Q18。

---

# 四、性能与瓶颈

## Q17：怎么判断瓶颈在哪？

**结论**：**改一个变量，看吞吐差多少**。不看 CPU 占用率。

**反例（真实踩过的坑）**：有一次 Redis 的 CPU 占用最高（0.66 核），我判定"瓶颈是 Redis"。后来把日志级别从 DEBUG 改回 INFO，吞吐从 3,883 涨到 10,900——真凶是**日志同步写盘压在请求线程上**。

**为什么会误判**：CPU 占用高只说明"它干活多"，不说明"别人在等它"。判断瓶颈要看**谁在排队**：Little's law（`吞吐 = 并发 ÷ 延迟`）里，延迟是被最慢的那一段决定的。

---

## Q18：消费端为什么只有 29 单/秒？

**结论**：因为一条消息的事务里包含 4 条 SQL + commit，其中 `UPDATE seckill_activity WHERE id=1` **持有行锁直到事务提交**。所有消费者抢同一行的锁，等于被串行化。

**证据**：并发 1/2/4 → 25.4 / 29.0 / 26.6 单/秒，单条消息耗时 39.4 / 68.9 / 150.6 ms。并发越高单条越慢，这是**排队**的典型特征，不是 CPU 不够。

**怎么办（没做）**：把活动库存的更新挪出事务、或者用 Redis 库存做权威不再回写活动表、或者按活动分片。

---

## Q19：双实例为什么吞吐不涨？

**结论**：因为瓶颈在**共享资源**上，不在应用进程里。

**实测**：200 并发下，单实例 10,575 QPS、双实例 10,452 QPS，基本一样。两个 JVM 抢的是同一个 Redis、同一份连接。

**所以双实例的意义**：**可用性**，不是吞吐。杀掉一个实例后 30 次请求全部成功，切换代价约 2 ms。

**这个问题答好很加分**：很多人会说"加机器就扩容了"，这里能说清"什么时候加机器没用"，是真实的工程判断。

---

## Q20：1000 并发的时候为什么大量连接被拒？

**结论**：Tomcat 的 `accept-count` 默认 100。200 个工作线程全忙时，新连接最多再排队 100 个，超出的直接 RST。压测时约 46% 拿到 connection refused。

**改法**：`server.tomcat.accept-count: 1000`。但这只是让瞬时建连能排队，**解决不了根本问题**——如果后端处理不过来，排队的请求最终还是超时。真正的解法是限制入口流量（限流/排队）。

# 五、可靠性（都有实测）

## Q21：Redis 挂了会怎样？

**结论**：**改之前会假死，改之后 1 秒内返回 503。**

| | 改前 | 改后 |
|---|---|---|
| 单个请求耗时 | **60,087 ms** | 1,043 ms |
| 响应 | HTTP 200 + `code:401 "Token解析失败"` | `code:503 "系统繁忙，请稍后重试"` |
| 恢复后首个请求 | 24,318 ms | 74 ms |

**为什么是 60 秒**：`spring.data.redis.timeout` 不配的话默认 60 秒。200 个工作线程全被占住，整个应用对外表现为假死。

**为什么改成 503 也重要**：401 是"你没登录"，503 是"服务暂时不可用"。**给错了错误码，调用方会做错误的决策**（重新登录 vs 重试）。

---

## Q22：MySQL 挂了会怎样？

**结论**：一条消息会占住消费线程很久。改之前 **115 秒**，改之后 **41 秒**。

**这笔账怎么算的**：`hikari.connection-timeout` 原来 20 秒 × 重试 5 次 + 退避 1+2+4+8 秒 = 115 秒。改成 5 秒 → 5×5+15 = 40 秒。

**关键取舍**：这两个数是**同一个数**——`connection-timeout` 越长，能自动扛住的停机时间越长，但每条消息占线程的时间也越长。选 5 秒的依据是：MySQL 容器重启实测 6.2 秒，40 秒有 6 倍余量；再长的停机是"故障"不是"重启"，应该告警 + 重放，不该指望消费线程干等。

**这个问题最能体现深度**：不是"我调了个参数"，而是"我知道这两个值互为代价，并且用实测数据选了边"。

# 六、安全与部署

## Q23：生产环境为什么要关 Swagger？

**结论**：SpringDoc 默认开着，`/v3/api-docs` 返回完整接口清单，`/swagger-ui/index.html` 是可交互的调用页面。部署到公网 IP 后实测两个都是 200。

**为什么危险**：等于把攻击面清单送给外面——有哪些接口、参数是什么、哪些不需要鉴权。

**坑**：本项目所有响应都是 HTTP 200 + 业务 `code`，所以**看 HTTP 状态码判断"关没关"是无效的**，必须看响应体。

---

## Q24：为什么数据库和应用的端口都只绑 127.0.0.1？

**结论**：公网只应该看到 80。3306 / 6379 / 8080 落在公网是最常见的事故来源。

**具体做法**：Docker 的 `-p 3306:3306` 默认绑 `0.0.0.0`，必须显式写 `127.0.0.1:3306:3306`；应用里配 `server.address: 127.0.0.1`，只让 Nginx 能访问它。

---

## Q25：密码和密钥放在哪？

**结论**：全部走环境变量，`application-prod.yml` 里只写 `${ENV}` 占位，**而且故意不给默认值**。

**为什么故意不给默认值**：给了默认值，漏配的时候应用会带着开发密码静默启动——你看到"启动成功"，实际连的是错的库、用的是弱密钥。宁可起不来。

**追问会到哪**：jar 里仍然打着开发配置（`application.yml`），但因为 prod profile 覆盖了所有敏感项，实际生效的是环境变量那套。
