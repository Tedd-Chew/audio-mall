# 瓶颈定位实验（E4）

目的：回答三个争论不清的问题 ——
1. 3,883 QPS 到底是"接口的上限"，还是"200 并发 × 51 毫秒"算出来的结果？
2. 接口的瓶颈是 Redis 还是别的东西？
3. 消费端 29 单/秒 是"这一行锁"造成的，还是"数据库整体性能不够"？

## 跑之前写下的预测（2026-11-03，先写后跑）

| # | 实验 | 变量 | 预测 | 预测错了说明什么 |
|---|---|---|---|---|
| 1 | Tomcat 线程 200 → 400，并发同步提到 400，压 60 秒 | 线程数 | QPS **6,000~7,500**（不到 2 倍），平均延迟涨到 **90~110 ms** | QPS 完全不动 → 还有我没想到的串行点 |
| 2 | 同一并发（200 VU、60 秒）压商品详情 `/api/product/1` | 换个接口 | QPS **4,500~5,500**（比秒杀高 15%~40%），延迟 35~45 ms | 如果高 2 倍以上 → 说明秒杀里 JWT 解析或 Lua 计算占了大头；如果更低 → 说明响应体大小的影响超过计算量 |
| 3 | 实验 1 跑的时候用 `docker stats` 采样 | — | Redis CPU **< 20%**、MySQL **< 10%** | Redis 逼近 100% → 那它真是瓶颈，我之前的推断全错 |

**三个实验共同的前提（要么说清，要么结论不算数）**：

- **k6 和被测应用在同一台机器上**，k6 自己也要吃 CPU。所以实验 1 里 QPS 涨不到 2 倍，原因可能是 k6 先撑不住了 —— 这一条属于"无法排除的干扰"，会写在结论里。
- 上次 3,883 QPS 那次压测：200 并发、60 秒、77,830 个请求，其中 **73,338 个（94%）被令牌桶挡掉**。所以那个数字测的是"限流拒绝路径"的吞吐，不是"真实抢购"的吞吐。实验 1 沿用同样的条件，保证可比。
- 用 `server.tomcat.threads.max` 做变量，其他一律不动。

## 实验 2 的设计细节

为什么选 `/api/product/1`：它是缓存命中的路径，请求只做两次 Redis 往返（`hasKey` 空值缓存 + `get` 详情缓存），**不碰数据库**；而秒杀接口也是两次 Redis 往返（`GET user:token` + `EVALSHA seckill.lua`）。

两次往返对两次往返，唯一的差别是：

| | 商品详情 | 秒杀 |
|---|---|---|
| Redis 往返 | 2（两条简单命令） | 2（一条 GET + 一条 Lua 脚本） |
| 脚本内部 | 无 | 约 6 个 `redis.call` |
| JWT 解析 | **不经过**（`/api/product/**` 在放行列表里） | 每个请求都解析一次 |
| 响应体 | 大（`description` 是 text） | 小（两个字段） |

所以这个对比能拆出两件事：**JWT 解析 + Lua 计算值多少**，和**响应体大小值多少**。两个因素方向相反，我押"计算量影响更大"，所以预测 product 更快。

# 实测结果（2026-11-03）

## 三个实验的预测 vs 实测

| # | 实验 | 预测 | 实测 | 判 |
|---|---|---|---|---|
| 1 | 线程 200→400，并发 200→400 | QPS 6,000~7,500 | **3,428（反而降了 12%）** | **错** |
| 2 | 200 并发压商品详情 | 比秒杀高 15%~40% | **高 193%（11,365 vs 3,883）** | **错** |
| 3 | 压测时采样 CPU | Redis < 20% | **Redis ≈ 48%** | **错，但方向对我有利** |

**三个预测全错，其中两个错得很彻底。** 这不是坏事 —— 说明这三个问题靠推理答不出来，只能测。

## 数据

| 场景 | 线程 | 并发 | QPS | 平均延迟 | 中位 | p95 | max |
|---|---|---|---|---|---|---|---|
| 秒杀接口 | 200 | 200 | 3,883 | 51.16 ms | 53.47 | 62.13 | 178.68 |
| 秒杀接口 | 400 | 400 | **3,428** | **116.24 ms** | 122.12 | 149.28 | 682.60 |
| 商品详情（缓存命中） | 200 | 200 | **11,365** | 17.17 ms | 16.19 | 25.79 | 158.92 |
| 秒杀接口（空载单请求） | — | 1 | — | 11.93 ms | — | — | — |
| 商品详情（空载单请求） | — | 1 | — | 6.82 ms | — | — | — |

压测中的 CPU 采样（5 次，线程 400 那轮）：

| 组件 | CPU（占单核百分比） |
|---|---|
| **Redis** | **46% ~ 53%（均值约 48%）** |
| MySQL | 0.9% ~ 1.1% |
| RabbitMQ | 0.3% ~ 1.5% |
| Java（应用进程） | 5.5% ~ 6.6% |

## 结论一：加线程不提吞吐，反而更差

线程 200→400、并发 200→400，QPS **从 3,883 掉到 3,428**，平均延迟**翻倍**（51 → 116 ms），max 从 179 ms 涨到 683 ms（长尾变粗）。

这是**串行资源 + 争用开销**的典型特征：多出来的 200 个线程没有并行干活，只是在同一个门口排更长的队，而且排队本身（上下文切换、连接争用）还要额外付钱。

所以原来那个「3,883 QPS」不是"随手测出来的中间值"，**它已经很接近上限了**。200 线程是这个场景的甜点。

## 结论二：瓶颈在 Redis（我上一轮的判断是错的）

**用户最初的直觉是对的：「瓶颈应该在 redis 这里吧」。我上一轮说「Redis 离饱和很远、不是瓶颈」，被这组数字否掉了。**

Redis 用了约 **48% 的一个核**，第二名 MySQL 只有 1%，差 48 倍。而且 Redis 是**单线程**执行命令的 —— 所有实例、所有请求都在同一个线程后面排队。

两个可以直接看到的佐证：

1. **同一个线程数（200）、同样的耗时（60 秒），商品详情能跑到 11,365 QPS，秒杀只有 3,883。** 两条路径都是两次 Redis 往返，差别在于秒杀每请求多做了：JWT 解析、`BizNoGenerator`、以及一次「限流令牌桶」的**写操作**（`HSET tokens` + `PEXPIRE`）。商品详情是纯读。
2. **空载单请求只差 5 毫秒（6.82 → 11.93），满载差 34 毫秒。** 差距随并发放大 7 倍 —— 这不是固定计算成本，是**排队成本**，而排的队是 Redis。

## 结论三：所以「双实例提吞吐」在本项目不成立

- 同一台机器上起两个实例，共享同一个 Redis → 不会更快。按上面的数据，**可能更慢**（等价于把线程从 200 加到 400，而那条路已经实测走不通）。
- 就算换成两台真机器，Redis 还是那一个 → 依然排在同一个线程后面。
- 想让接口真的更快，只有两条路，**都不是加机器**：
  1. **减少每个请求的 Redis 往返**。现在每请求 2 次（`GET user:token` + `EVALSHA seckill.lua`）。去掉 JWT 那次 GET（改成纯验签 + 本地缓存），理论上能把吞吐往 6,000~7,000 推 —— 这是下一步最值得做的优化，而且**能讲**。
  2. **把限流从 Redis 里挪走**，或者让限流对"被拒绝的请求"不写 Redis（现在是每请求都 `HSET` 一次令牌桶，即使被拒）。

**所以双实例的真正定位就是用户说的那句：不只是、也不需要为了吞吐 —— 是为了高可用和滚动发版。** 这次的实测数据正好给了它一个硬证据：*"我实测过，加并发不提吞吐，所以我的双实例不是为了吞吐。"*

## 未查清的部分（不要讲得比事实满）

- **Redis 只用了 48%，为什么就顶住了？** 按 CPU 看还有一倍余量。所以顶不完全在 Redis 的 CPU 上。嫌疑（**全部未验证**）：Lettuce 单连接多路复用在 400 线程下的争用；每请求一次 Redis 写（`appendonly yes` 的 AOF 路径）；容器网络转发开销。要定位得做分段计时，这次没做。
- k6 和被测应用在同一台机器，k6 自己也吃 CPU。线程 400 那轮 k6 的 CPU 没单独量，所以"降了 12%"里有多少是 k6 先撑不住，说不清。
- 三次压测的"被限流比例"都在 94% 左右（令牌桶 200/s 的补充速度），所以这些数字测的是「限流拒绝路径」的吞吐。真实抢购路径的吞吐没有单独测。
