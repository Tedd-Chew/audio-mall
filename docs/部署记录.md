## 1. 拓扑

```
用户
 │  80
 ▼
Nginx（Docker，host 网络）──────► 应用（systemd，java -jar，127.0.0.1:8080）
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
              MySQL 8.0            Redis 7.4           RabbitMQ 3.13
              （Docker）           （Docker）          （机器上原有容器，复用）
              127.0.0.1:3306       127.0.0.1:6379      127.0.0.1:5672
```

**为什么应用不进容器**：这台机器只有 3.6 GB 内存，多一层容器网络没有收益；
而 `systemctl status` / `journalctl` 的排查比 `docker logs` 直接，改配置也只需
`systemctl restart audio-mall`。中间件进容器是因为它们需要"删干净重来"的方便。

**为什么端口全部绑 127.0.0.1**：公网只应该看到 80。3306/6379/8080 落在公网是
最常见的事故来源，而 Docker 的 `-p 3306:3306` 默认就是绑 0.0.0.0 —— 必须显式写
`127.0.0.1:3306:3306`。

## 4. 首次部署步骤

```bash
# 1. 本地打包（服务器上没有 Maven，也不必装）
mvn -q clean package -DskipTests

# 2. 上传
scp target/audiobackend-0.0.1-SNAPSHOT.jar  ubuntu@106.54.35.197:/opt/audio-mall/app.jar
scp -r deploy/*                            ubuntu@106.54.35.197:/opt/audio-mall/

# 3. 服务器上
cd /opt/audio-mall
mkdir -p sql logs/nginx data
cp sql/01-init.sql sql/02-order.sql sql/03-seed.sql sql/    # 见下方说明
chmod 600 app.env .env
sudo docker compose up -d
sudo cp audio-mall.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now audio-mall
```

注意 `docker-entrypoint-initdb.d` **只在数据目录为空时执行**。要重建库：
`sudo docker compose down && sudo rm -rf data/mysql && sudo docker compose up -d`。

## 5. 每个"不做就会坏"的证据（全部实测）

### 5.1 不写 `application-prod.yml` → 生产带着开发配置跑

jar 里打进去的是 `application.yml`（本地开发配置）。不覆盖的话，生产会带着：

| 项 | 开发值 | 后果 |
|---|---|---|
| `mybatis.configuration.log-impl` | `StdOutImpl` | 每条 SQL 打到控制台，同步 IO 压在请求线程上。**这是压测时把吞吐从 10,900 拖到 3,883 QPS 的那个配置**，而且看起来像业务代码慢 |
| `jwt.expire-time` | 7 天 | token 7 天不失效，等于没有会话管理 |
| `jwt.secret` / `payment.callback-secret` | 写在文件里的固定值 | 拿到 jar 就能伪造 token 和支付回调 |
| `datasource.url` | `localhost:3307` | 连不上（容器内是 3306） |

`application-prod.yml` 里所有敏感项都写成 `${ENV}` **且不给默认值** ——
故意让漏配时启动失败，而不是带着弱配置"看起来正常"。

### 5.2 不关 Swagger → 接口清单直接对公网开放

实测关闭前 `GET /v3/api-docs` 返回完整 OpenAPI 文档、`/swagger-ui/index.html`
是可交互的调用页面，两者对外都是 200。关闭后同样两个地址返回的是业务错误包装
（`{"code":500,...}`），拿不到任何接口信息。

> 顺带一个坑：看 HTTP 状态码判断"关没关"是无效的 —— 本项目所有响应都是
> HTTP 200 + 业务 `code`，必须看响应体。

### 5.3 不做 swap → 3.6 GB 内存没有兜底

加 swap 前 `Swap: 0B`。OOM killer 在内存打满时是**直接杀进程**，不是变慢；
而 systemd 会把应用重新拉起，但 MySQL 容器被 OOM 杀了，恢复要重新走一次
InnoDB 启动。加 2 GB swap 后，瞬时峰值只会表现为变慢。

### 5.4 共用 RabbitMQ 的 admin 账号 → 应用起不来

第一次启动直接失败：

```
Caused by: com.rabbitmq.client.AuthenticationFailureException:
  ACCESS_REFUSED - Login was refused using authentication mechanism PLAIN.
Caused by: org.springframework.amqp.AmqpIllegalStateException: Fatal exception on listener startup
```

那个跑了 6 个月的 `admin` 账号密码未知（不是本地那个），也不该改别人的密码。
正确做法是给应用单独建账号：

```bash
sudo docker exec rabbitmq rabbitmqctl add_user audiomall <密码>
sudo docker exec rabbitmq rabbitmqctl set_permissions -p / audiomall ".*" ".*" ".*"
```

> 教训：**"机器上已经有中间件"不等于"能直接用"**。先验证认证，再谈复用。
> 顺带一提，应用是**在监听器启动阶段**就失败退出的（不是"能起来但收不到消息"），
> 所以错误很显眼；如果换成惰性连接，问题会藏到第一次下单才暴露。

### 5.5 Redis 健康检查没传环境变量 → 永远 `health: starting`

先看 compose 里 `$` 的个数决定变量在**谁的进程**里展开：

| 写法 | 谁展开、什么时候 | 能读到什么 |
|---|---|---|
| `${REDIS_PASSWORD}` | docker compose 自己，解析 YAML、创建容器**之前** | `.env` 文件和宿主机环境变量 |
| `$$REDIS_PASSWORD` | 容器里的 shell，健康检查执行**那一刻** | 只能读容器**自己**的环境变量（`environment:` 声明的） |

`$$` 的意思是"别在这儿展开，留一个真 `$` 传进去"。

最初写的是：密码只出现在 `command` 里（由 compose 展开成明文，传给 `redis-server`），
**没有进容器的环境变量**。于是健康检查里的 `$REDIS_PASSWORD` 展开成空字符串，
等价于执行 `redis-cli -a "" --no-auth-warning ping`，实际输出是：

```
AUTH failed: WRONGPASS invalid username-password pair or user is disabled.
NOAUTH Authentication required.
```

输出里没有 `PONG` → `grep -q PONG` 返回 1 → 判定失败。
**Redis 服务本身一直正常，坏的是检查器。**

修法是给 service 加容器内环境变量：

```yaml
environment:
  REDIS_PASSWORD: ${REDIS_PASSWORD:?...}
```

对照：MySQL 的健康检查也用了 `$$MYSQL_ROOT_PASSWORD`，但它的密码**本来就是**
由 `environment:` 传进去的（官方镜像要靠它初始化），所以容器内能读到，检查一直是过的。
差别不在写法，在这个变量有没有真的进容器的环境。

**为什么这个坑值得单独记**：它的症状是"服务是好的，但系统说它坏"。
看到 `unhealthy` 你会去查 Redis 日志、内存、认证配置——方向全错。
更严重的情况是写了 `depends_on: redis: condition: service_healthy` 时，
应用会永久起不来，而你会以为是 Redis 挂了。

一句话：**健康检查是一条独立的代码路径，它自己也会坏；它坏掉时是"误报"，比不报更骗人。**

### 5.6 不加 `Restart=always` → 进程死了没人管

只有一个实例，没有 Nginx 后面的第二个实例兜底。实测 `kill -9` 主进程后：

```
killed at 23:42:53 → RECOVERED after 12s（systemd RestartSec=5 + 启动 6 秒）
```

`SuccessExitStatus=143` 是为了让 `systemctl stop`（SIGTERM）不被记成失败。

## 7. 业务链路验证（实测）

在服务器上跑的完整流程：

1. `POST /api/user/register` 注册买家 → 返回 token
2. `POST /api/order/seckill/1?requestId=<uuid>` → `{"orderNo":"ORD...","message":"排队中，请稍候"}`
3. 同一个 `requestId` 再发一次 → **同一个 orderNo**，提示"重复提交，这是你上次抢到的订单"
4. 日志：`秒杀订单创建成功，orderNo=ORD1793720553466001，金额=99.00`
5. 数据库：`orders` 表 1 行，`status=0`（待支付），`total_amount=99.00`
6. Redis：`audio:seckill:stock:1` = **99**（原 100），`audio:seckill:bought:1` 是 Hash
7. MQ 队列 `audio.seckill.order.queue` 消费后为空

说明 Lua 扣减 → 入队 → 手动 ack 消费 → 写库这条链路在服务器上是通的。

## 9. 已知问题 / 没做的

| 问题 | 说明 |
|---|---|
| 仍只有**一个**应用实例 | 进程级故障靠 systemd 拉起（12 秒）；机器级故障没有备份，这是单机部署的固有代价 |
| Nginx 没做限流 | 本地决定过先不做；现在公网可达，理论上可以被刷 |
| MQ 队列里有历史残留 | `ai_question_queue`、`llm_test_queue` 是旧应用留下的，不影响本应用 |
| `/opt/audio_backend` 旧 jar 还在 | 已停止运行，文件保留以便回滚到旧系统 |
| 404 会被包成 500 | 未匹配的路由落进 `GlobalExceptionHandler`，对外表现为 `code:500`；监控时刻意区分需要额外处理 |
| 没有健康检查端点 | Nginx 的 `/health` 直接代理到 `/api/product/1`，能用但不是标准做法 |
| 上传的图片目录是空的 | `upload.base-path` 指到 `/opt/audio-mall/uploads`，但种子里商品的 `cover_img` 为 null，所以商品没有图 |

## 10. 部署后的容量实测

完整设计、预期、推翻过程见 `docs/压测记录.md` 的 "Sprint 6"。这里只放结论。

| 场景 | 吞吐 | 平均延迟 | 瓶颈 |
|---|---|---|---|
| 公网（本机 k6 → 3 Mbps 带宽） | **419 次/秒** | 510 ms | 带宽 3 Mbps |
| 服务器回环 → 应用 8080 | **7,214 次/秒** | 14.2 ms | 4 核打满（其中压测工具占 1.86 核） |
| 服务器回环 → 经 Nginx 80 | **5,159 次/秒** | 19.8 ms | 同上 + Nginx 开销 |

三条要点：

1. **瓶颈排序是 带宽 → CPU → 代码。** 前两层与代码无关，本地压测永远测不出来。
2. **Nginx 在这一层吃掉 28% 吞吐**。本地 16 线程时看不出来，4 核上是真成本。
3. **这台机器对外约 900 次/秒封顶**：`3 Mbps ÷ 8 ÷ 400 B ≈ 940`。
   这个数由买的带宽决定，跟 Redis、跟秒杀设计都没关系。

7,214 是**下限**：压测工具和应用抢同一台机器。真实外部流量时应用可用的核更多，
但那个数没有测到，所以不写。
