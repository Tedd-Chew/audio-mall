# 双实例实验

## 跑之前写下的预测（2026-11-03 20:50）

**目的**：回答两个问题 ——

1. 两个实例共享同一个 Redis，**会不会超卖**？
2. 双实例的 QPS 到底涨不涨？

**变量**：上游有几个实例（1 个 vs 2 个）。

**常量**：200 并发、60 秒、库存 100、限购 1、每个实例 Tomcat 200 线程、日志 INFO、同一个 Nginx（8000）、同一台机器。

**为什么要跑两轮**：历史上那个 3,883 QPS 是在**日志 DEBUG** 下测的（每秒 570KB 同步写盘）。现在日志级别降到 INFO，直接和历史数字比会把两个变量混在一起。所以跑一轮「单实例经 Nginx」、一轮「双实例经 Nginx」，除了实例数其他全同。

另外：单实例那轮不是"停掉 8081"，而是把 Nginx 的 upstream 改成一个节点。停掉实例的话 Nginx 每 5 秒会重试一次死节点，每次先耗 2 秒连接超时才转移，会污染延迟数据。

| 指标 | 单实例经 Nginx | 双实例经 Nginx |
|---|---|---|
| QPS | 3,600~3,900（比直连略低，多了一跳 Nginx） | **3,600~4,300**，涨不超过 20% |
| 平均延迟 | 50~60 ms | 50~110 ms |
| 成功订单数 | 恰好 100 | **恰好 100** |
| DB / Redis 库存 | 都是 0 | **都是 0** |
| 两实例各接多少 | — | 各约 50% |

**核心预测**：双实例的 QPS **到不了 2 倍**，甚至可能和单实例持平。

理由：`docs/瓶颈定位实验.md` 里实测过 —— Redis 只用了 0.5 个核但吞吐不再涨（线程 200→400 时 QPS 反而从 3,883 掉到 3,428），说明瓶颈是"所有请求都要过 Redis 这道门"，而两个实例共享同一个 Redis。

**如果这条预测成立**，这轮实验就给出了这一整段最重要的那句话：

> 我实测过双实例不提升吞吐，所以我的双实例是为了高可用，不是为了 QPS。

**会写的数据**：库存、订单（跑完删）、Redis 的 `seckill:*` 键。

# 实测结果（2026-11-03 20:51–20:54）

## 数据

| 配置 | QPS | 平均延迟 | 中位 | p95 | max | 订单数 |
|---|---|---|---|---|---|---|
| 单实例经 Nginx | **10,575** | 18.63 ms | 18.76 | 27.87 | 250.03 | 100 |
| 双实例经 Nginx | **10,452** | 18.84 ms | 19.38 | 29.06 | 145.63 | 104 |

压测中采样（双实例那轮）：

| 组件 | 占用 |
|---|---|
| Redis | 58% ~ 72%（约 0.65 个核） |
| Java（两个进程合计） | 2.26 ~ 3.21 个核，全机 16 核 |
| MySQL | 约 1% |

两实例分发正常（Nginx 日志里 8080 / 8081 交替）。

## 结论一：这一轮证明不了"双实例不提吞吐"，因为压测端先到顶了

两个配置差 1%，在噪声内。但**不能**据此说"双实例没用"——算一下就明白：

```
200 个并发 ÷ 18.8 ms = 10,600
```

**测出来的 10,452 和 10,575 正好等于这个数。** 意思是：200 个虚拟用户全部处于"在飞"状态，QPS 完全由"客户端并发数 ÷ 单请求耗时"决定，服务端还有多少余力根本没被压出来。

要测服务端上限，得把并发提到 400 甚至 800。这一轮**没做到**，所以结论只能是：

> 在 200 并发下，单实例和双实例吞吐一样（都被压测端卡住）。双实例的上限**未测出**。

## 结论二：真正的大发现 —— 日志级别值 2.7 倍吞吐

单实例这次跑到 **10,575 QPS**，而历史上同样的 200 并发、200 线程只测到 **3,883**。两次之间，服务端唯一的大改动是：

> 把 `com.example.audiobackend` 的日志级别从 **DEBUG** 降到 **INFO**。

降掉的是一条每请求都会执行的日志：

```java
// JwtInterceptor.java:89
log.debug("Token校验通过，用户ID：{}，URI：{}", userId, requestUri);
```

为什么一行日志能压掉 2.7 倍吞吐（**推断，未做 A/B 验证**）：

1. logback 的 `OutputStreamAppender` 在写的时候会**加锁**（`synchronized`），200 个 Tomcat 线程抢的是**同一把锁** → 日志写入变成一个串行点。
2. `FileAppender` 是**同步写**，写盘发生在请求线程上。实测 3,428 QPS 时日志速率约 570 KB/s、10MB 文件每 17 秒滚一次。
3. 滚动（rotation）时还要重命名文件，比平时更贵。

**所以这是一次典型的"看到一个数字就归因"的错误**：详见下面「推翻的结论」。

## 推翻的结论：`docs/瓶颈定位实验.md` 里"瓶颈是 Redis"是错的

原来那轮实验（线程 200→400，QPS 3,883→3,428）我归因为"Redis 是瓶颈，因为它的 CPU 占用 48%、第二名 MySQL 只有 1%"。

**现在同一套代码、同样的并发，Redis 占用 58%~72% 却能跑 10,452 QPS。** 如果 Redis 真的是 3,883 时的瓶颈，它不可能在 2.7 倍流量下只多用 20 个百分点。

真实情况是：**3,883 那个上限是 DEBUG 日志的同步写 + logback 的锁造成的**。Redis 当时"最忙"只是因为它是一个真实干活的下游，而日志锁恰好卡在每一个请求上。

这个错误的教训值得记下来：

> **"哪个组件 CPU 占用最高"不等于"哪个组件是瓶颈"。**
> 瓶颈是"吞吐不再增加的那个原因"。日志锁完全不进 CPU 统计（它表现为线程阻塞在锁上），所以只看 CPU 排行永远找不到它。

**正确的做法**：改一个变量，看吞吐动多少。日志级别这一个变量就把吞吐从 3,883 抬到 10,575 —— 这才是找到瓶颈的方法，比看 CPU 排行榜可靠。

## 还没验证的（下一步）

1. **日志级别的 A/B**：起一个实例带 `--logging.level.com.example.audiobackend=DEBUG`，再跑一轮 60 秒，看 QPS 是否跌回 4,000 附近。约 3 分钟。
2. **双实例的真实上限**：把并发提到 400 / 800 再比一次。注意 Windows 上 300 个瞬时连接会被 listen backlog 拒掉一部分，可能要分批。
