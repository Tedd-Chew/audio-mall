## E1 消费者进程崩溃，消息会不会丢（2026-11-02 实测）

> **结论：消息只有 `basicAck` 之后才被删。进程被硬杀、连接一断，broker 把未确认的消息重新投出去；重投不会建两张单，因为 `order_no` 唯一索引挡住了第二次 insert。**

**目的**：验证手动 ack 在最坏情况（进程直接死掉）下成立 —— 如果这条不成立，多实例、重试、死信全都没意义。

**变量**：消费者处理消息期间强杀进程。

**常量**：库存 100、限购 1、单实例。

**怎么制造「正在处理」**：先把 `seckill_activity.stock` 改成 0，让消费端 `decreaseStock` 返回 0 → 抛异常 → 进入 1/2/4/8 秒的重试窗口。窗口有 15 秒，足够在中间下刀。

**指标**：队列 `messages` / `messages_unacknowledged`、订单数、DB 活动库存、Redis 库存。

**预期（跑之前写下）**：杀进程后未确认数归 0、消息数回到 1；重启后消息被消费，订单建成，两边库存都是 99。

**数据**：

| 时刻 | messages | unacked | 说明 |
|---|---|---|---|
| 杀之前 | 1 | 1 | 消费者拿着消息在重试 |
| 强杀后 6 秒 | 1 | 0 | broker 发现连接断了，把消息收回队列 |
| 重启后 | 0 | 0 | 消息被消费掉：订单数 1、DB 99、Redis 99 |

**前提（说清楚，别当成无条件成立）**：Windows 上 `Stop-Process -Force` 是 `TerminateProcess`，不走优雅关闭，Spring 的 shutdown hook 没有执行 —— 所以这是真崩溃，不是"假装崩溃"。

**为什么重试不会建两张单**：`orders` 上有 `uk_order_no`。第二次 insert 撞索引抛 `DuplicateKeyException`，消费端判定为"同一条消息重复投递"直接 ack。唯一索引在这里同时充当「上一次到底提交没有」的判定器。

## E2 依赖故障行为表

问题：秒杀链路上挂了三个依赖（Redis、MySQL、RabbitMQ），停掉其中任何一个，用户看到什么、数据会怎样。
每个场景都是：`reset.ps1` → 停依赖 → 发 1 次秒杀 → 记录 → 恢复容器 → 不重启应用再发 1 次。

### 跑之前写下的预测（2026-11-02，先写后跑，跑完不改）

**E2-1 停 Redis**

1. 秒杀请求**到不了业务代码**：`JwtInterceptor` 第 71 行 `get(user:token:{id})` 先抛 `RedisConnectionFailureException`，被第 92 行那个泛 `catch (Exception)` 包成 `BusinessException(401, "Token解析失败：...")`。所以用户拿到的是 **HTTP 200 + code 401**，看着像"登录失效"，而不是"系统繁忙"。依赖挂了被伪装成鉴权失败 —— 这是预测里最难看的一条。
2. 响应应该很快（< 1 秒）：容器停了 TCP 直接 RST，不会等满 60 秒的 command timeout。
3. 订单数不变，Redis 库存不变（没执行到 Lua），MQ 也没有新消息。
4. `docker start` 回来后**不重启应用**，再发一次应当正常返回「排队中」：Lettuce 懒重连，没有失效的连接工厂；而且 Redis 有 volume + `appendonly yes`，key 都还在，不需要重新预热。
5. 未查清：共享连接被 RST 之后，头一两批请求会不会撞上一个重连窗口。

**E2-2 停 MySQL**

1. 秒杀接口**照常返回「排队中，请稍候」** —— 这条路径只碰 Redis 和 RabbitMQ，一次 SQL 都没有。Redis 库存 -1。
2. 消费者建单失败。每次失败前要先等 Hikari 的 `connection-timeout: 20000`（池里连接全死了，拿不到新连接就等满 20 秒），所以 **到达死信的时间 ≈ 4×20 + (1+2+4+8) ≈ 95 秒**，而不是重试策略上写的 15 秒。这个数最值得实测：重试间隔是我们自己写的，但每次失败本身有多贵不是。
3. 恢复 MySQL 后**不会自动补单**：消息躺在 DLQ 里没人重放。用户看到过"排队中"，但永远查不到订单，Redis 名额被永久吃掉（少卖一件）。
4. MySQL 停着期间 `OrderTimeoutTask`（每分钟）和 `SeckillActivityCloseTask` 会刷错误日志。

**E2-3 停 RabbitMQ**（2026-11-02 已实测过一半，这次复验新代码）

1. 秒杀返回「排队失败，请重试」，Redis 库存回到 100，幂等门被删。
2. 应用不退出，监听容器每 5 秒重连一次刷日志。
3. 恢复后不用重启应用，消费自动恢复。

**注意**：跑每个实验前先 `reset.ps1`，跑完恢复容器并等 healthy。

### 实测结果（2026-11-02，与上面的预测对照）

**一句话版**

| 停掉什么 | 用户看到 | 数据会怎样 |
|---|---|---|
| Redis | **等 60 秒**，然后「Token解析失败：Redis command timed out」（code 401） | 没有任何写入；故障被伪装成"你的登录失效了" |
| MySQL | 「排队中，请稍候」+ 订单号，**60 毫秒就返回** | 名额被扣、订单永远不存在；消息 115 秒后进死信，恢复后**不自动补**，要人工重放 |
| RabbitMQ | 「排队失败，请重试」，**33 毫秒返回** | 名额立刻还回去，幂等门被删，什么都不用修 |

三种故障，只有 RabbitMQ 那种是"报错报对了"。另外两种：一个把故障说成鉴权失败，一个把失败说成排队成功。

**E2-1 停 Redis**

| 请求 | 耗时 | 返回 |
|---|---|---|
| 刚停（连接还挂着） | 60,087 ms | `{"code":401,"msg":"Token解析失败：Redis command timed out"}` |
| 再发一次 | 60,031 ms | 同上 |

- **预测里写"应该 < 1 秒"，实测 60 秒，预测错了。** 原因（推测，未查清）：`docker stop` 之后容器端口映射还挂在宿主上，SYN 被吞掉而不是回 RST，所以走的是 Lettuce 的 60 秒命令超时，不是"连接被拒立即失败"。
- 订单数不变、MQ 队列 0 —— 请求死在 `JwtInterceptor` 第 71 行，根本没到业务代码。
- 恢复：`docker start` 后 0.9 秒 `PING` 通。**不重启应用**，但第一个请求仍花了 **24,318 ms** 才成功，第二个才回到 **13 ms**。所以"自动恢复"成立，但恢复后有一段约 20 秒的尾巴（连接重建窗口，机制未查清）。
- 必须记住的推论（未实测）：每个被拖住的请求占掉一个 Tomcat 线程 60 秒，200 个工作线程全被占满时整个应用对外表现为假死。

**E2-2 停 MySQL**

- 接口 **60 ms** 返回 `排队中，请稍候 ORD1793609890437006`，Redis 库存 100→96 —— 秒杀路径确实一次 SQL 都不碰，所以它照样放行。
- 消费端的时间线（日志时间戳，与"5 次尝试"对得上）：

| 尝试 | 时刻 | 距上次 | 说明 |
|---|---|---|---|
| 第 1 次失败 | 16:58:30 | 20 s | 等满 Hikari `connection-timeout: 20000` |
| 第 2 次 | 16:58:51 | 21 s | 20 s + 退避 1 s |
| 第 3 次 | 16:59:13 | 22 s | 20 s + 退避 2 s |
| 第 4 次 | 16:59:37 | 24 s | 20 s + 退避 4 s |
| 第 5 次失败 → nack | 17:00:05 | 28 s | 20 s + 退避 8 s，然后进死信 |

- **115 秒进死信**（5×20 + 1+2+4+8），接口日志里是 `HikariPool-1 - Connection is not available, request timed out after 20000ms`。预测写的是 95 秒（按 4 次算），实测 115 秒 —— 是 5 次尝试。
- 恢复 MySQL（6.2 秒 healthy）后等 10 秒：**订单数仍然为 0，`activity.stock`=97、Redis=96**，差的这一件就是被吃掉的。
- 从死信重放（`POST /api/queues/%2F/audio.seckill.order.dlq/get` + 重新投回 `audio.seckill.exchange`，返回 `routed:true`）→ 订单建成，`activity.stock`=96，与 Redis 一致。**消息没丢，但补单是人工动作，不是系统行为。**
- 这条最值得讲：**把一个依赖挂掉，系统不会停，它会把失败包装成成功。**

**E2-3 停 RabbitMQ**

- 接口 **33 ms** 返回 `排队失败，请重试`，订单号为 null；Redis 库存 96→96（扣了又还），该 requestId 的幂等门已被删（`--scan` 查不到 `e2-nomq-*`）。
- 应用没退出，商品接口照常 200；监听容器每 5 秒重连刷日志。
- 恢复（6.2 秒 healthy）后不重启应用，19 ms 抢到名额并成功建单，`activity.stock`=95 = Redis 95。

### 改完重测（同日 17:20–17:27，同一套实验）

改了三处：`spring.data.redis.timeout: 1s`、`hikari.connection-timeout: 5000`、`JwtInterceptor` 里把 `RedisConnectionFailureException`/`QueryTimeoutException` 单独捕获并报 503（原来落到泛 `catch` 里被包成 401）。

| 指标 | 改前 | 改后 | 倍数 |
|---|---|---|---|
| Redis 停机时单请求耗时 | 60,087 ms | **1,043 ms** | 58 倍 |
| Redis 停机时的错误码 | 401「Token解析失败」 | **503「系统繁忙」** | — |
| Redis 恢复后第一个请求 | 24,318 ms（要等连接重建） | **74 ms** | 328 倍 |
| MySQL 停机到进死信 | 115 s | **41 s** | 2.8 倍 |
| MySQL 停机时接口耗时 | 60 ms | 25 ms | — |

- 改后 MySQL 那组的重试间隔实测是 6 / 7 / 9 / 13 秒，正好等于「5 秒 Hikari + 1/2/4/8 秒退避」。41 秒 = 5×5 + 15 + 轮询误差。
- 改后**仍然不会自动补单**（恢复 10 秒后订单还是 0），重放后 `activity.stock` 和 Redis 都回到 98，一致。
- **意外收益**：Redis 恢复后 24 秒的尾巴消失了。原因是命令超时从 60 秒降到 1 秒后，那条坏掉的连接会立刻被判定失败并重建，而不是让请求一直挂在上面。

**原来那三条待办的处置**：

1. ~~Redis 不可用时 60 秒才失败且报 401~~ —— **已修**（超时 1s + 单独 catch 报 503）。
2. ~~MySQL 不可用时一条消息占线程 115 秒~~ —— **已修**（`connection-timeout` 20s → 5s）。
3. 死信没有告警、没有自动重放 —— **仍未做**，"人工补单"目前是手工调管理接口。

**顺带观察**：跑完之后库存自己从 95 变回 96，查日志是 `OrderTimeoutTask` 在 17:01:21 把 16:55 创建的那张未支付单关掉了 —— 关单会同时把库存还给 **DB 和 Redis**（两边各 +1），所以两边重新对齐。这也复现了预测第 4 条：MySQL 停机期间这个定时任务确实报错（17:00:21 那轮没跑成）。

## E3 消费端 2 个线程能吃多少单

**问题**：`concurrency: 2` 够不够用？用户问的是"消费得过来吗"。

**跑之前的预测（2026-11-02，先写后跑）**：

- 一条消息在消费端是 4 条 SQL（条件 UPDATE 活动库存、查商品、插 orders、插 order_items）+ 一次提交。猜单条 5~15 毫秒，2 个线程 → **130~400 单/秒**。
- 300 条消息应该在 **1~2.5 秒**内清空，峰值积压接近 300。
- 300 条全部成单，`activity.stock` 正好减 300，没有重复单。
- **预期不准的地方**：这个环境把 `innodb_flush_log_at_trx_commit` 设成了 2（模拟生产磁盘，见 `ISSUES.md`），提交事务不真刷盘，**测出来的消费吞吐偏乐观**，不能当生产数字用。

**设计**：

| 项 | 取值 |
|---|---|
| 变量 | 一次灌入 300 条消息 |
| 常量 | `concurrency: 2`、`prefetch: 10`、库存 1000 |
| 怎么灌 | 走真实入口：300 个不同用户各抢 1 次（`k6 MODE=consume`），令牌桶容量 500 所以全部放行 |
| 怎么量 | 日志里「秒杀抢到名额并入队」（到达）和「秒杀订单创建成功」（完成）各带毫秒时间戳，两条曲线相减就是积压曲线 |
| 指标 | 吞吐（单/秒）、单条平均耗时、峰值积压、清空总时长 |

**为什么绕开商品详情之类的干扰**：这一轮只看消费端，接口侧的影响在 E2 里已经量过了。

### 实测结果（2026-11-02 17:24–17:26）

> **结论：2 个消费线程约 25~30 单/秒，而且加线程没用 —— 并发 1、2、4 的吞吐都在 25~29 单/秒，只有单条耗时线性变长。瓶颈是 `UPDATE seckill_activity` 那一行：所有订单抢同一行，数据库把它们排成一条队。**

| 场景 | 吞吐 | 有效单条 | 说明 |
|---|---|---|---|
| 空载，只发 1 条 | — | **13.0 ms** | 端到端（入队 → 建单提交），机器空闲 |
| 积压 50 条，并发 1 | 25.4 单/秒 | 39.4 ms | 单线程，没有锁竞争 |
| 积压 50 条，并发 2 | **29.0 单/秒** | 68.9 ms | 比单线程只快 14%，在噪声边缘 |
| 积压 200 条，并发 2 | 29.4 单/秒 | 68.1 ms | 和 50 条几乎一样 → 不是积压拖慢的 |
| 积压 50 条，并发 4 | 26.6 单/秒 | 150.6 ms | 吞吐不涨，单条翻倍 |

- 到达很干净：200 条消息在 **73 毫秒**内全部入队，峰值积压 200，所以「跨度 × 并发 ÷ 条数」算出来的单条耗时可信。
- **并发 4 比并发 1 还慢**，且单条从 39 毫秒涨到 151 毫秒 —— 多出来的全是排队等行锁的时间。这就是「线程池加得越多越快」这个直觉在这里失效的原因。
- 空载 13 ms 和带载 39 ms 的差别是压测机和被测应用在同一台机器上：50 个并发 HTTP 请求正在跑 Lua 和 JSON，消费端的 SQL 往返被 CPU 抢了。
- 300 个 VU 的版本跑不起来：Windows 的 listen backlog 直接把连接 RST 掉（`connectex: actively refused`），实测两次都是。200 个 VU 零拒绝。这个坑 `seckill.js` 的注释里早就记过，我又踩了一次。

**换算成「够不够用」**：

| 库存件数 | 清空时间（按 29 单/秒） |
|---|---|
| 100 件 | 3.4 秒 |
| 1,000 件 | 34 秒 |
| 10,000 件 | 5.7 分钟 |

音响商城一次放 100~1000 件，**2 个线程够用，不需要动**。要是真到上万件，加线程没用，得换库存模型（把一行拆成 N 个桶、或让 Redis 当唯一扣减口径、DB 只做流水）。

**被推翻的预测**：跑之前猜单条 5~15 毫秒、2 线程 130~400 单/秒，实测 68 毫秒 / 29 单/秒，差了 4~14 倍。原因是当时按「4 条 SQL 各 1~3 毫秒」估的，没算上所有订单串在同一行锁上。

### 机制补充：锁被持有到事务结束，不是到 UPDATE 结束（2026-11-02 追问后补）

`OrderServiceImpl.createSeckillOrder` 上有 `@Transactional(rollbackFor = Exception.class)`，方法体是：

```
① UPDATE seckill_activity SET stock = stock - 1 WHERE id = 1   ← 这里拿到 id=1 的行锁
② INSERT orders
③ SELECT product WHERE id = ?
④ INSERT order_item
⑤ INSERT payment
⑥ COMMIT                                                        ← 到这里才放锁
```

InnoDB 的排他行锁不是语句级的，**是持有到事务提交**。所以线程 B 在 ① 这一步堵住的时长 = 线程 A 跑完 ②③④⑤ 再提交的时长，不是一条 UPDATE 的时长。

两个直接结论：

- **串行的不是「一条 UPDATE」，是「整笔事务」**。这就是并发 1 时单条 39 毫秒的来源 —— 一条 UPDATE 本身远到不了 39 毫秒。
- **加线程只会加长队列**：并发 2 时单条 69 毫秒、并发 4 时 151 毫秒，多出来的全是等锁（挂起线程、进等待队列、被唤醒、重新检查）的时间，吞吐一点不涨，因为真正的临界区没有变短。

这是典型的**热点行更新**。真正的瓶颈是「一行 + 长事务」这两个条件同时成立，去掉任何一个都能提速：

| 去掉哪个条件 | 做法 | 代价 |
|---|---|---|
| 缩短事务 | 把 ① 挪出大事务单独提交，锁只持有 1~2 毫秒 | 失去原子性，**消息重试会重复扣**，必须加一张按 `order_no` 去重的扣减流水表 |
| 拆开那一行 | `seckill_activity` 按 `userId % N` 拆成 N 行桶 | 余量要 `SUM`、关单要还到正确的桶、活动配置跟着改 |
| 不更新行 | 每单插一行扣减流水，余量 = 总量 − `COUNT(*)`；不同主键，没有热点行 | 查余量要聚合，或者维护汇总表（又变成热点行） |

**为什么现在不做**：1000 件货按 29 单/秒是 34 秒卖完，够用；而这三个方案每个都会新增一条错误路径（重复扣、桶选错、余量聚合不一致）。没有真实压力就换吞吐，是拿正确性冒险。

**顺带**：这条链路上其实有两个库存口径 —— Redis 的 Lua（真正的闸门，把 1000 个人挡到 100 个）和 DB 这一行（最终裁决 + 可对账）。DB 这一行只负责「记账」，却成了串行点，所以「缩短事务」那个方案在理论上成立。

## 附：商品缓存的现状（2026-11-02 核对代码）

只有**商品详情**走缓存，其它都直达 MySQL：

| 场景 | 走哪里 | IO 次数 |
|---|---|---|
| `GET /api/product/{id}` 命中 | Redis | `hasKey` + `get` + 异步 `INCR` 浏览数 |
| 同上未命中 | MySQL | 商品表 1 次 + **分类表 1 次**，然后写缓存 |
| 查不存在的 id | Redis 空值缓存 | 1 次 `hasKey` 就返回，不碰库 |
| 商品列表 / 分页 | **MySQL，无缓存** | `COUNT` + 分页查询 |
| 秒杀消费者建单 | **MySQL，绕过缓存** | `productMapper.selectById`，每单 1 次 |
| 后台增删改 | MySQL，改完删缓存 | `delete(product:{id})` + `delete(product:null:{id})` |

两个可以聊的点：

1. **`hasKey` + `get` 是两次 Redis 往返**，可以合并成一次 `GET`（空值缓存写特殊标记再判断）。详情 QPS 没测过，所以先不改。
2. **分布式锁是被注释掉的**，注释里写明了原因：老实现有两个 bug（`finally` 里不校验持有者就删锁、抢不到锁就递归调用自己会栈溢出），判断是"一把写错的锁比没有锁更危险"。代价是热门商品缓存失效瞬间没有保护（击穿），当前量级不需要，推到多实例时再启用。
