## 三、可能被追问的问题

> 这里只放 9 条最常用的。完整版（25 条，按幂等/库存/MQ/性能/可靠性/安全分组，
> 每条含"结论 → 为什么 → 追问会到哪"）见 `docs/面试问答.md`。

### Q1：为什么用 Lua，不能在 Java 里先查库存再扣？

"查"和"减"是两个 Redis 命令，中间隔着一次网络往返。两个请求同时读到 `stock=1`，就会都减一次，卖出 2 件。Lua 在 Redis 内部是单线程执行的，中间不可能插进别的命令，所以检查和扣减变成一个原子操作。

### Q2：Lua 已经扣了 Redis 库存，为什么还要 MQ？

Redis 快但不可靠（可能丢、可能重启），订单必须落到 MySQL。如果直接在请求线程里写 MySQL，等于把数据库暴露在瞬时大流量下，而且请求响应时间会被数据库拖住。MQ 的作用是把「抢名额」和「建订单」解耦：请求线程只做 Redis 那一下，返回"排队中"；落库由消费端按自己的速度做，这就是削峰。

### Q3：撞唯一索引怎么区分「重复投递」和「真实冲突」？

- 撞 `uk_order_no`：同一个 orderNo 的订单已经在库里 —— 说明这条消息被重复投递，订单早建好了，**ack 即可**。
- 撞 `uk_user_request`：同一用户同一 requestId 已有另一张单 —— 说明这个用户真的抢到了另一单，本次是多余的，**必须回滚 Redis 名额**。

判据是"按 order_no 能不能查到"。不能一律当成重复，否则会把"真实冲突"也当成功，名额就永久少了一个。

### Q4：为什么手动 ack，不自动 ack？

自动 ack 是"消息一到就确认"。如果这时候进程崩了或者写库失败，消息已经没了，订单就丢了。手动 ack 是"处理成功之后才确认"，做不到就不确认，消息会回到队列重投。代价就是 Q3 那个问题——重投意味着可能重复消费，所以需要幂等兜底。这两件事是配套的。

### Q5：两个实例同时抢，会不会超卖？

不会。库存的唯一权威是 Redis 里那个 key，两个实例操作的是同一份数据；扣减在 Lua 里原子执行，检查与扣减之间没有窗口。应用本身是无状态的，不带任何本地库存缓存。

### Q6：Nginx 为什么不用 ip_hash 做会话保持？

因为应用是无状态的：登录态在 Redis（`audio:user:token:{userId}`），库存、幂等键也都在 Redis。任何一个实例都能处理任何请求，所以用默认轮询即可。用 ip_hash 反而会让负载不均。

### Q7：瓶颈是怎么定位的？

方法是"一次只改一个变量，看吞吐差多少"，不是看谁的 CPU 高。有一次我以为瓶颈是 Redis（它 CPU 最高），后来把日志级别从 DEBUG 调回 INFO，吞吐从 3,883 涨到 10,900，才知道是同步写盘卡在请求线程上。**CPU 占用最高 ≠ 瓶颈**，排队的那个才是。

### Q8：那 10,900 QPS 的可信度？

限定条件是本机 8C16T、Windows + Docker Desktop、200 并发、纯读接口。换到 4 核云服务器上，公网只有 419（带宽 3 Mbps 是硬顶），回环 7,214（压测工具自己还占了 1.86 核）。**不同环境的数字不能直接比**，所以我简历上不写绝对 QPS。

### Q9：如果现在让你优化，你会做什么？

按代价从低到高：
1. `requestId` 改成必填（现在是可选，Nginx 重试时同一个 POST 可能被处理两次）
2. 死信队列加监控/重放工具（现在消息进 DLQ 没人知道）
3. 消费端那条 `UPDATE seckill_activity WHERE id=1` 的行锁持有到事务提交，实测只有 29 单/秒，是消费侧的真空档
4. 加带宽或上 CDN——现在公网 900 次/秒就顶住了，跟代码无关

## 五、一分钟项目介绍（背这个）

"这是一个音响商城的后端，我重点做了秒杀链路。核心是三层：第一层用 Redis Lua 把限流、库存、限购、幂等一次原子做完，保证不会超卖也不会重复下单；第二层用 MQ 异步落库削峰，消费端手动 ack，失败退避重试，重试耗尽进死信；第三层用数据库唯一索引兜底，因为消息可能重复投递。我做这个项目的方法是先让它坏——比如关掉 Redis、杀掉 MySQL，看我设计的东西是不是真的扛住了，每次实验都记在 docs 里。"
